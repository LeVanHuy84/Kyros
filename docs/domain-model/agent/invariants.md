# Business Invariants — AI Agent Bounded Context

---

## Validation Rules

### INV-AGENT-01 — Mandatory User Confirmation Before Execution

| Aspect | Detail |
| --- | --- |
| **Rule** | No `PlanStep` may begin execution until the associated `ApprovalRequest` has a status of `Approved`. |
| **Enforcement** | `beginExecution()` on `AgentSession` requires the resolved `ApprovalStatus = Approved` to be passed as a command parameter. The aggregate rejects execution if approval is not confirmed. |
| **Violation** | Execution attempt without approval rejected; session remains in `AwaitingApproval`. |

---

### INV-AGENT-02 — Re-planning Ceiling

| Aspect | Detail |
| --- | --- |
| **Rule** | The number of automatic re-planning attempts must not exceed **3**. On the 4th attempt trigger, the session must transition to `Escalated` instead of re-planning. |
| **Enforcement** | `replan()` checks `replanCount`. If count is already 3, `escalate()` is called instead of incrementing and re-planning. `ReplanAttemptCount` value object validates `0..3`. |
| **Violation** | A 4th re-planning cycle must never execute. Escalation must occur. |

---

### INV-AGENT-03 — Execution Ordering and Dependency Constraint

| Aspect | Detail |
| --- | --- |
| **Rule** | Plan steps must be executed strictly according to their defined dependency order. A step may only begin (`markStepRunning`) when all its `StepDependency` prerequisites have status `Succeeded`. |
| **Enforcement** | `markStepRunning(stepId)` evaluates all `StepDependency` links on the `PlanStep` entity and verifies each referenced step's status is `Succeeded` before transitioning to `Running`. |
| **Violation** | Step execution out of order is rejected at the aggregate level. |

---

### INV-AGENT-04 — Acyclic Dependency Graph

| Aspect | Detail |
| --- | --- |
| **Rule** | The dependency graph among `PlanStep` entities must be acyclic (a DAG). Circular dependencies would cause deadlock in execution ordering. |
| **Enforcement** | `attachPlan(steps)` validates the dependency graph for cycles before the plan is accepted. |
| **Violation** | Plan with cyclic step dependencies is rejected; session remains in `Planning`. |

---

### INV-AGENT-05 — GoalText Must Be Non-Empty

| Aspect | Detail |
| --- | --- |
| **Rule** | A session's `GoalText` must be non-empty after trimming. |
| **Enforcement** | `GoalText` value object rejects blank strings; `startSession()` validates before creating the aggregate. |
| **Violation** | Session creation rejected. |

---

### INV-AGENT-06 — Plan Must Have at Least One Step

| Aspect | Detail |
| --- | --- |
| **Rule** | A `PlanSnapshot` presented for approval and a plan attached to a session must contain at least one `PlanStep`. |
| **Enforcement** | `attachPlan(steps)` rejects an empty step list; `PlanSnapshot` value object validates non-empty step list on construction. |
| **Violation** | Empty plan attachment rejected; `PlanGenerated` not published. |

---

## Consistency Rules

### INV-AGENT-07 — Workspace Tenant Boundary

| Aspect | Detail |
| --- | --- |
| **Rule** | All sessions, plans, and approval requests must belong to a single `WorkspaceId`. An agent session may only invoke tools operating on entities within its own workspace. |
| **Enforcement** | `WorkspaceId` is immutable on each aggregate after creation. Tool parameter validation enforces that target entity references belong to the same workspace. |
| **Violation** | Cross-workspace tool invocation rejected. |

---

### INV-AGENT-08 — Tool Registry Exclusivity

| Aspect | Detail |
| --- | --- |
| **Rule** | The executor must only invoke capabilities registered in the `Tool Registry`. Direct database modification or service calls that bypass the registry are prohibited. |
| **Enforcement** | `ToolReference` on each `PlanStep` is validated against the registry at plan attachment time. The executor resolves and calls only registered tool adapters. |
| **Violation** | A step referencing an unregistered tool is rejected at plan attachment. Execution of unregistered tools is an architectural defect. |

---

### INV-AGENT-09 — Strict Grounding Rule (RAG)

| Aspect | Detail |
| --- | --- |
| **Rule** | Answers generated by the agent must be grounded in retrieved user documents. If no documents exist in context, the agent must respond with "I do not know" rather than fabricating information. Every assertion must carry a `GroundingCitation`. |
| **Enforcement** | Application layer enforces citation requirement before presenting RAG responses. `GroundingCitation` is required on response artifacts; absent sources trigger the "I do not know" fallback path. |
| **Violation** | Ungrounded assertions constitute a correctness defect. |

---

### INV-AGENT-10 — ApprovalRequest is Immutable After Resolution

| Aspect | Detail |
| --- | --- |
| **Rule** | An `ApprovalRequest` in `Approved`, `Rejected`, or `Expired` status cannot be re-resolved. Only `Pending` approvals may be acted upon. |
| **Enforcement** | `approve()`, `reject()`, and `expire()` guard on `status = Pending`. Terminal statuses are immutable. |
| **Violation** | Re-resolution of a settled approval is rejected. |

---

### INV-AGENT-11 — GoalText is Immutable for Session Lifetime

| Aspect | Detail |
| --- | --- |
| **Rule** | The `GoalText` on an `AgentSession` is set at creation and cannot be changed, even through re-planning cycles. Re-planning produces new steps but the original goal remains constant. |
| **Enforcement** | No `updateGoal()` operation exists on the aggregate. `GoalText` is set only in `startSession()`. |
| **Violation** | Architectural guardrail — altering the goal mid-session would invalidate the coherence of the execution trace. |

---

### INV-AGENT-12 — Terminal Session States Accept No Further Operations

| Aspect | Detail |
| --- | --- |
| **Rule** | Sessions in `Succeeded`, `Failed`, or `Escalated` status must not accept plan attachments, step transitions, or re-planning commands. |
| **Enforcement** | All mutating operations guard on `status not in {Succeeded, Failed, Escalated}`. |
| **Violation** | Operation on a terminal session is rejected. |
